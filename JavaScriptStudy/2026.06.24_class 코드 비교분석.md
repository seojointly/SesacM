# 두 코드 비교 분석 및 리팩토링 포인트

## 1. 결론

강사님의 코드가 객체 지향 프로그래밍(OOP)의 확장성과 자바스크립트 문법 관점에서 더 안정적인 구조입니다.

본인 코드에는 실제 동작 오류(Bug)와 함께 유지보수 측면에서 개선이 필요한 부분들이 존재합니다.

---

## 🔴 본인 코드의 치명적인 오류 (Bug)

### 1) getSummary() 내 메서드 호출 누락

본인 코드의 `CartItem` 클래스 내부 `getSummary()`를 보면 다음과 같이 작성되어 있습니다.

```javascript
${this.getTotalPrice}
```

하지만 메서드를 실행하려면 반드시 괄호 `()`가 필요합니다.

```javascript
${this.getTotalPrice()}
```

괄호가 없으면 함수 실행 결과가 아니라 함수 객체 자체가 문자열로 출력됩니다.

---

### 2) DiscountCartItem의 확장성 상실

현재 할인율이 아래와 같이 고정되어 있습니다.

```javascript
#discountRate = 0.5;
```

이 구조에서는 오직 **50% 할인 상품**만 생성할 수 있습니다.

예를 들어,

- 10% 할인
- 20% 할인
- 30% 할인

등 다양한 할인율을 적용할 수 없습니다.

즉, 상속 구조를 만들었음에도 재사용성과 확장성이 크게 떨어집니다.

---

## 🟡 리팩토링 관점에서 개선할 부분

### 1) 매개변수 순서 통일 (기본값 파라미터 규칙)

본인 코드

```javascript
constructor(name, quantity = 1, price)
```

강사님 코드

```javascript
constructor(name, price, quantity = 1)
```

일반적으로 자바스크립트에서는 **기본값이 없는 필수 파라미터를 먼저 배치**하고, **기본값이 있는 파라미터를 뒤쪽에 배치**합니다.

본인 코드의 경우 가격만 전달하려면 다음과 같이 작성해야 합니다.

```javascript
new CartItem('TV', undefined, 500000);
```

반면 강사님 코드는

```javascript
new CartItem('TV', 500000);
```

처럼 훨씬 직관적으로 사용할 수 있습니다.

---

### 2) 캡슐화와 부모 메서드 활용 (super 사용)

본인 코드는 `DiscountCartItem`에서 출력 문자열을 새로 조합했습니다.

반면 강사님 코드는

```javascript
super.getSummary()
```

를 활용하여 부모 클래스가 이미 만들어 둔 출력 형식을 그대로 재사용합니다.

이 방식의 장점은 다음과 같습니다.

- 코드 중복 감소
- 유지보수 편의성 향상
- 부모 로직 변경 시 자동 반영

즉, 객체 지향 관점에서 훨씬 바람직한 구조입니다.

# 코드 라인별 비교 및 의미 분석

## ① 생성자(Constructor)와 파라미터 순서

### 강사님 코드

```javascript
constructor(name, price, quantity = 1)
```

### 본인 코드

```javascript
constructor(name, quantity = 1, price)
```

### 분석

강사님은

- 필수값: `name`, `price`
- 선택값: `quantity`

순으로 배치했습니다.

덕분에

```javascript
new CartItem('TV', 500000)
```

처럼 수량을 생략할 수 있습니다.

반면 본인 코드는 수량을 생략하고 가격만 전달하기 어려운 구조입니다.

---

## ② 메서드 내부에서의 private 필드(#) vs Getter 접근

### 강사님 코드

```javascript
return this.#price * this.#quantity;
```

### 본인 코드

```javascript
return this.#price * this.#quantity;
```

### 분석

본인 코드의 주석에

> 여기서는 # 큰 차이 없다

라고 작성되어 있는데 반은 맞고 반은 틀립니다.

클래스 내부에서는 `#private` 필드에 직접 접근해도 문제없습니다.

하지만 중요한 점은 부모의 `#private` 필드는 자식 클래스가 상속받지 못한다는 것입니다.

예시:

```javascript
class Parent {
  #price = 100;
}

class Child extends Parent {
  test() {
    console.log(this.#price); // 오류
  }
}
```

따라서 자식 클래스나 외부에서는 반드시 Getter를 사용해야 합니다.

```javascript
this.price
```

---

## ③ 자식 클래스(DiscountCartItem)의 필드 선언 및 생성자

### 강사님 코드

```javascript
#discountRate;

constructor(name, price, quantity = 1, discountRate = 0) {
  super(name, price, quantity);
  this.discountRate = discountRate;
}
```

### 본인 코드

```javascript
#discountRate = 0.5;

constructor(name, quantity, price) {
  super(name, quantity, price);
}
```

### 분석

강사님 코드는

- 할인율을 외부에서 입력받음
- Setter를 통한 유효성 검사 수행
- 다양한 할인율 지원

이 가능합니다.

반면 본인 코드는

```javascript
#discountRate = 0.5;
```

로 고정되어 있어

- 확장성 부족
- Setter 검증 미사용
- 할인율 변경 불가

라는 문제가 있습니다.

---

## ④ 자식 클래스의 getTotalPrice() 오버라이딩

### 강사님 코드

```javascript
return (super.price * super.quantity) - ...
```

### 본인 코드

```javascript
const originalPrice = this.price * this.quantity;

return originalPrice * (1 - this.#discountRate);
```

### 분석

수학적 표현만 놓고 보면 본인 코드가 더 직관적입니다.

```javascript
가격 × (1 - 할인율)
```

이라는 형태가 일반적인 할인 계산식과 동일하기 때문입니다.

다만 강사님은

```javascript
super.price
super.quantity
```

를 사용하여 부모 클래스의 프로퍼티를 참조하고 있음을 명확하게 표현했습니다.

참고로 자바스크립트에서는

```javascript
this.price
```

로 접근해도 부모 Getter를 찾아가기 때문에 본인 코드 역시 정상 동작합니다.

---

## ⑤ 자식 클래스의 getSummary() 오버라이딩

### 강사님 코드

```javascript
return `${super.getSummary()} | 할인율: ${this.#discountRate}%`;
```

### 본인 코드

```javascript
return `${this.name} 50% 세일 | 단가: ${this.price}
| 수량: ${this.quantity}
| 할인가: ${this.getTotalPrice()}`;
```

### 분석

두 코드의 가장 큰 차이점입니다.

강사님은 부모의 결과물을 재사용합니다.

```javascript
super.getSummary()
```

예를 들어 부모가

```text
TV | 단가: 500000 | 수량: 2 | 총액: 1000000
```

을 반환한다면,

자식은 여기에

```text
| 할인율: 20%
```

만 추가하면 됩니다.

반면 본인 코드는 부모의 출력 형식을 무시하고 처음부터 다시 작성했습니다.

이 경우 부모의 출력 형식이 변경되면

```text
| → -
```

같은 단순한 수정이라도 자식 클래스까지 모두 찾아서 수정해야 합니다.

즉,

- 코드 중복 증가
- 유지보수 비용 증가
- 변경 전파 문제 발생

이라는 단점이 생깁니다.

# 최종 정리

## 본인 코드의 장점

- 할인 계산식이 직관적임
- 기본적인 클래스 상속 구조 이해는 잘 되어 있음

## 반드시 수정해야 할 부분

- `this.getTotalPrice` → `this.getTotalPrice()`
- 할인율을 생성자로 입력받도록 수정
- Setter를 통한 유효성 검사 적용
- 생성자 파라미터 순서 개선

## 강사님 코드에서 배워야 할 부분

- `super.getSummary()` 활용
- 코드 재사용성 확보
- 부모 클래스 로직 재활용
- 확장 가능한 설계
- 유지보수를 고려한 OOP 구조

한 줄로 정리하면,

> 본인 코드는 "동작은 하지만 확장성이 부족한 코드"이고, 강사님 코드는 "상속과 캡슐화를 제대로 활용한 OOP 스타일의 코드"라고 볼 수 있습니다.
