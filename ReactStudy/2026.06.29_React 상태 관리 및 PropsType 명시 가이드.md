# React 상태 관리 및 Props/Type 명시 가이드

이 문서는 React의 **Props Drilling** 문제점과 이를 해결하기 위한 다양한 상태 관리 방식(React 내장 기능 및 외부 라이브러리), 그리고 **JSDoc을 활용한 타입 명시의 이유**를 정리한 문서입니다.

---

# 1. Props Drilling과 해결 방식

## Props Drilling이란?

**Props Drilling**이란 상위 컴포넌트의 데이터를 하위 컴포넌트로 전달하기 위해 중간 컴포넌트들이 단순히 Props만 전달하는 현상을 말합니다.

컴포넌트 구조가 깊어질수록

- 유지보수가 어려워지고
- 중간 컴포넌트가 불필요한 Props를 계속 전달해야 하며
- 코드의 가독성이 떨어집니다.

이를 해결하는 방법은 크게 두 가지입니다.

1. React 내장 기능 사용
2. 외부 상태 관리 라이브러리 사용

---

# 2. React 내장 기능으로 해결

## ① Context API (`useContext`)

Context API는 React에서 제공하는 전역 데이터 공유 기능입니다.

중간 컴포넌트를 거치지 않고 필요한 컴포넌트에서 직접 데이터를 사용할 수 있습니다.

### 예제

```jsx
import React, { createContext, useContext, useState } from 'react';

// 1. Context 생성
const DataContext = createContext();

export const App = () => {
  const [data] = useState("Hello World from Context!");

  return (
    <DataContext.Provider value={data}>
      <CompOne />
    </DataContext.Provider>
  );
};

const CompOne = () => {
  return (
    <div>
      <h3>CompOne</h3>
      <CompTwo />
    </div>
  );
};

const CompTwo = () => {
  return (
    <div>
      <h3>CompTwo</h3>
      <CompThree />
    </div>
  );
};

const CompThree = () => {
  const data = useContext(DataContext);

  return (
    <div>
      <h3>CompThree : {data}</h3>
    </div>
  );
};
```

### 장점

- Props Drilling 제거
- React 기본 기능이라 별도 라이브러리 필요 없음

### 단점

- Context 값이 변경되면 Consumer들이 다시 렌더링될 수 있음
- 상태가 많아질수록 Context가 복잡해질 수 있음

---

## ② Component Composition (children 활용)

Props를 계속 전달하는 대신 **구조를 조립하는 방식**입니다.

중간 컴포넌트는 데이터를 전혀 몰라도 되고, 단순히 `children`만 렌더링합니다.

### 예제

```jsx
import React from 'react';

export const App = () => {
  const data = "Hello World from Composition!";

  return (
    <CompOne>
      <CompTwo>
        <CompThree data={data} />
      </CompTwo>
    </CompOne>
  );
};

const CompOne = ({ children }) => {
  return (
    <div>
      <h3>CompOne</h3>
      {children}
    </div>
  );
};

const CompTwo = ({ children }) => {
  return (
    <div>
      <h3>CompTwo</h3>
      {children}
    </div>
  );
};

const CompThree = ({ data }) => {
  return (
    <div>
      <h3>CompThree : {data}</h3>
    </div>
  );
};
```

### 장점

- Props Drilling 감소
- 컴포넌트 재사용성이 높아짐
- 구조적으로 매우 깔끔한 패턴

### 단점

- 복잡한 상태 공유에는 적합하지 않음
- children 구조가 지나치게 깊어질 수 있음

# 3. 외부 상태 관리 라이브러리

규모가 큰 프로젝트에서는 전역 상태 관리 라이브러리를 많이 사용합니다.

| 라이브러리 | 특징 |
|------------|------|
| Zustand | 가장 가볍고 사용법이 단순함. Provider가 필요 없음. |
| Redux Toolkit (RTK) | Redux 공식 권장 방식. 대규모 프로젝트에서 많이 사용됨. |

---

## ① Zustand

독일어로 **상태(State)** 를 의미합니다.

현재 React 생태계에서 가장 인기 있는 상태 관리 라이브러리 중 하나입니다.

### 예제

```jsx
import create from 'zustand';

const useDataStore = create((set) => ({
  data: "Hello World from Zustand!",

  updateData: (newData) =>
    set({
      data: newData
    })
}));

export const App = () => {
  return <CompOne />;
};

const CompOne = () => <CompTwo />;

const CompTwo = () => <CompThree />;

const CompThree = () => {

  const data = useDataStore((state) => state.data);

  return (
    <div>
      <h3>CompThree : {data}</h3>
    </div>
  );
};
```

### 장점

- 매우 간단한 API
- Provider 불필요
- 러닝 커브가 낮음
- 작은 프로젝트부터 대규모 프로젝트까지 사용 가능

---

## ② Redux Toolkit (RTK)

기존 Redux의 복잡한 설정을 개선한 공식 패키지입니다.

### 예제

```jsx
import { createSlice, configureStore } from '@reduxjs/toolkit';
import { Provider, useSelector } from 'react-redux';

const dataSlice = createSlice({

  name: 'dataStore',

  initialState: {
    value: "Hello World from Redux Toolkit!"
  },

  reducers: {

    setValue: (state, action) => {
      state.value = action.payload;
    }

  }

});

const store = configureStore({

  reducer: {

    dataStore: dataSlice.reducer

  }

});

export const App = () => {

  return (

    <Provider store={store}>
      <CompOne />
    </Provider>

  );

};

const CompOne = () => <CompTwo />;

const CompTwo = () => <CompThree />;

const CompThree = () => {

  const data = useSelector(
    (state) => state.dataStore.value
  );

  return (

    <div>
      <h3>CompThree : {data}</h3>
    </div>

  );

};
```

### 장점

- 대규모 프로젝트에 적합
- DevTools 지원
- 상태 추적이 쉬움
- 규칙이 명확하여 협업에 유리

### 단점

- Zustand보다 코드가 많음
- 초보자에게는 러닝 커브가 있음

# 4. JSDoc을 사용하는 이유

JavaScript는 타입이 없는 언어입니다.

브라우저는 JSDoc이 없어도 정상적으로 실행됩니다.

그럼에도 JSDoc을 작성하는 이유는 **개발 생산성과 유지보수성 향상** 때문입니다.

---

## ① Props Type 명시

```jsx
/**
 * @typedef {Object} ChildrenProps
 * @property {React.ReactNode} children
 */
```

### 사용하는 이유

- VS Code 자동 완성(IntelliSense)
- Props 오타 방지
- 협업 시 문서 역할
- 유지보수성 향상

마우스를 올리기만 해도

- 어떤 Props를 받아야 하는지
- 자료형은 무엇인지

바로 확인할 수 있습니다.

---

## ② React.FC 타입 명시

```jsx
/**
 * @type {React.FC<ChildrenProps>}
 */
const GiftCard1 = (props) => {

};
```

### 사용하는 이유

#### 1. React 컴포넌트임을 명시

일반 함수가 아니라 React Function Component라는 것을 에디터가 인식합니다.

---

#### 2. Props 자동 완성

```jsx
props.
```

만 입력해도

```text
children
```

등의 속성을 자동으로 추천합니다.

---

#### 3. React 규칙 검사

에디터가

- JSX 반환 여부
- 컴포넌트 명명 규칙
- Props 타입

등을 미리 검사하여 오류를 줄여줍니다.

---

# 정리

## Props Drilling 해결 방법

| 방식 | 특징 |
|------|------|
| Context API | React 기본 기능으로 전역 데이터 공유 |
| Component Composition | children을 활용하여 구조적으로 해결 |
| Zustand | 가장 간단한 전역 상태 관리 |
| Redux Toolkit | 대규모 프로젝트 표준 상태 관리 |

---

## JSDoc을 사용하는 이유

- 자동 완성 지원
- 타입 추론
- 협업 문서 역할
- 유지보수 향상
- React 컴포넌트 규칙 검사
- 런타임 이전에 오류 발견 가능

---

# 결론

- 작은 프로젝트 → Context API 또는 Component Composition
- 중·대규모 프로젝트 → Zustand 또는 Redux Toolkit
- JavaScript 프로젝트에서도 JSDoc을 활용하면 TypeScript 수준의 개발 편의성을 일부 누릴 수 있으며, 협업과 유지보수 측면에서도 큰 장점을 제공합니다.
