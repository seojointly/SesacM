# 왜 Setter를 지양할까?

초보 시절에는 보통 이렇게 작성한다.

```java
user.setName("김철수");
user.setEmail("kim@test.com");
user.setStatus("ACTIVE");
```

문제는 엔티티의 상태가 왜 변경되는지 알 수 없다는 것이다.

---

## Setter 방식의 문제

```java
user.setStatus("CANCEL");
```

질문

- 회원 탈퇴인가?
- 주문 취소인가?
- 관리자 강제 차단인가?
- 휴면 계정 전환인가?

코드만 보고 의도를 알 수 없다.

---

## 비즈니스 메서드 방식

```java
public void cancelMembership() {
    this.status = Status.CANCEL;
}
```

사용

```java
user.cancelMembership();
```

코드를 보는 순간

"회원 탈퇴 처리"

라는 의미를 알 수 있다.

---

## 유지보수 차이

Setter

```java
user.setStatus(Status.CANCEL);
```

---

비즈니스 메서드

```java
user.cancelMembership();
```

몇 달 뒤에 다시 봐도 의미가 명확하다.

---

# 비즈니스 로직을 엔티티 안에 넣는 이유

Setter 방식

```java
user.setStatus(Status.CANCEL);
user.setUpdatedAt(LocalDateTime.now());
```

서비스마다 중복 발생

---

비즈니스 메서드 방식

```java
public void cancelMembership() {
    this.status = Status.CANCEL;
    this.updatedAt = LocalDateTime.now();
}
```

사용

```java
user.cancelMembership();
```

변경 규칙을 엔티티가 직접 관리한다.

---

# Setter를 완전히 금지해야 할까?

아니다.

실무에서는 보통

```java
@Getter
```

는 열어둔다.

---

```java
@Setter
```

는 거의 안 쓴다.

---

필요한 경우에만

```java
changeName()
changeEmail()
changeAddress()
```

같은 메서드를 제공한다.

---

# Builder를 엔티티에 붙여도 될까?

가능하다.

실제로 많이 사용한다.

---

예시

```java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class User {

    private String name;

    private String email;

    @Builder
    public User(
        String name,
        String email
    ) {
        this.name = name;
        this.email = email;
    }
}
```

---

사용

```java
User user =
    User.builder()
        .name("홍길동")
        .email("hong@test.com")
        .build();
```

---

# 그런데 엔티티 Builder를 싫어하는 회사도 있다

이유는

"엔티티를 아무 곳에서나 생성하게 될 수 있기 때문"

---

예시

```java
User.builder()
    .name("홍길동")
    .email("hong@test.com")
    .build();
```

누구나 생성 가능

---

그런데 실제 비즈니스 규칙은

```java
가입 시 반드시 상태 ACTIVE

가입 시 가입일 자동 입력

가입 시 기본 권한 USER
```

일 수 있다.

---

Builder만 열어두면

```java
User.builder()
    .name("홍길동")
    .build();
```

이상한 객체 생성 가능

---

# 그래서 정적 팩토리 메서드를 선호하기도 한다

```java
public static User createUser(
    String name,
    String email
) {
    return User.builder()
        .name(name)
        .email(email)
        .status(Status.ACTIVE)
        .role(Role.USER)
        .createdAt(LocalDateTime.now())
        .build();
}
```

---

사용

```java
User user =
    User.createUser(
        "홍길동",
        "hong@test.com"
    );
```

---

장점

필수값 누락 방지

비즈니스 규칙 보장

# DTO에는 Builder를 적극 사용

실무에서 Builder를 가장 많이 붙이는 곳

사실 엔티티보다 DTO다.

---

Request DTO

```java
@Builder
public class UserCreateRequest {

    private String name;

    private String email;
}
```

---

Response DTO

```java
@Builder
public class UserResponse {

    private Long id;

    private String name;

    private String email;
}
```

---

사용

```java
UserResponse response =
    UserResponse.builder()
        .id(user.getId())
        .name(user.getName())
        .email(user.getEmail())
        .build();
```

---

# 엔티티 Builder vs DTO Builder

| 구분 | 엔티티 | DTO |
|--------|--------|--------|
| Builder 사용 | 회사마다 다름 | 거의 필수 수준 |
| 상태 관리 | 중요 | 중요하지 않음 |
| 비즈니스 규칙 | 존재 | 없음 |
| 자유 생성 | 위험 | 안전 |
| 실무 선호도 | 상황에 따라 | 매우 높음 |

---

# 실무에서 가장 흔한 구조

## 엔티티

```java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class User {

    private String name;

    private String email;

    public static User createUser(
        String name,
        String email
    ) {
        User user = new User();

        user.name = name;
        user.email = email;

        return user;
    }

    public void changeEmail(
        String email
    ) {
        this.email = email;
    }
}
```

---

## DTO

```java
@Getter
@Builder
public class UserResponse {

    private Long id;

    private String name;

    private String email;
}
```

---

# 면접 한 줄 정리

Setter는 객체 상태를 무분별하게 변경할 수 있어 지양하고, 의도가 명확한 비즈니스 메서드(changeEmail(), cancelMembership())를 사용한다.

Builder는 객체 생성 가독성을 높여주므로 DTO에서는 적극 사용하며, 엔티티에서는 비즈니스 규칙 보장 여부에 따라 Builder 또는 정적 팩토리 메서드를 선택한다.
