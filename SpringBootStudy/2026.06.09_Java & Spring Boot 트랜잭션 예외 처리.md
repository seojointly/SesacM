# Java & Spring Boot 트랜잭션 예외 처리 가이드

스프링 부트(Spring Boot)의 `@Transactional` 환경에서 **실행 예외(RuntimeException)**와 **일반 예외(Checked Exception)**에 따른 롤백(Rollback) 메커니즘과 두 예외의 차이점을 상세히 정리한 가이드입니다.

---

## 1. 예외 메커니즘과 트랜잭션 기본 동작

Spring의 트랜잭션 관리자인 `PlatformTransactionManager`는 예외가 발생했을 때 내부적으로 다음과 같은 정책을 기본값으로 사용합니다.

| 구분 | 실행 예외 (Runtime / Unchecked) | 일반 예외 (Checked) |
| :--- | :--- | :--- |
| **최상위 부모 클래스** | `java.lang.RuntimeException` | `java.lang.Exception` (`RuntimeException` 제외) |
| **컴파일러 체크 여부** | 체크 안 함 (실행 중에 확인) | **필수 체크** (`try-catch` 또는 `throws` 강제) |
| **스프링 기본 롤백 여부** | **O (자동 Rollback)** | **X (기본은 Commit)** |
| **예외의 의미(철학)** | 복구 불가능한 시스템 오류 / 개발자 실수 | 주변 환경에 의해 발생할 수 있는 예측 가능한 상황 |

---

## 2. 예외별 상세 설명 및 대표적인 예시

### ① 실행 예외 (Runtime Exception / Unchecked Exception)
> **스프링 기본 동작: 자동 롤백 (Rollback)**

개발자의 실수나 프로그램 논리 오류로 인해 **런타임(실행 중)**에 발생하는 예외입니다. 프로그램이 정상적으로 더 이상 진행될 수 없는 심각한 오류로 판단하여, Spring은 데이터 일관성을 지키기 위해 **트랜잭션을 즉시 롤백**합니다.

*   **`NullPointerException` (NPE)**
    *   객체 인스턴스를 생성하거나 주입받지 않은 상태(null)에서 멤버 메서드나 변수에 접근할 때 발생합니다.
*   **`IllegalArgumentException` / `IllegalStateException`**
    *   메서드에 부적절한 인자(Argument)가 전달되었거나, 메서드를 호출하기에 적절하지 않은 객체 상태일 때 발생합니다.
*   **`ArithmeticException`**
    *   숫자를 `0`으로 나누는 등 수학적으로 불가능한 연산을 수행할 때 발생합니다.
*   **`IndexOutOfBoundsException`**
    *   배열(Array)이나 리스트(List)의 범위를 벗어난 잘못된 인덱스에 접근할 때 발생합니다.

### ② 일반 예외 (Checked Exception)
> **스프링 기본 동작: 롤백 안 함 (Commit)**

파일 시스템, 네트워크, 데이터베이스 연결 등 **애플리케이션 외부 환경과의 상호작용** 과정에서 발생할 수 있는 예외입니다. 자바 문법상 반드시 예외 처리를 코드상에 명시해야 컴파일이 가능합니다. 

자바와 스프링의 설계 철학상, Checked Exception은 에러라기보다 **"비즈니스적으로 충분히 일어날 수 있는 예외 상황이니 개발자가 직접 복구하거나 대안 흐름을 제어하라"**는 하나의 신호(Return text)로 취급됩니다. 따라서 스프링은 트랜잭션을 취소하지 않고 그대로 **커밋(Commit)**합니다.

*   **`IOException`**
    *   파일을 읽거나 쓸 때 파일이 존재하지 않거나, 시스템 권한이 부족하여 입출력에 실패할 때 발생합니다.
*   **`ClassNotFoundException`**
    *   `Class.forName()` 등을 통해 특정 클래스를 동적으로 로드하려 했으나, 해당 클래스 파일(`.class`)을 찾지 못했을 때 발생합니다.
*   **`SQLException`**
    *   데이터베이스 내부 오류나 잘못된 SQL 문법으로 인해 발생합니다.
    *   *참고: 스프링 프레임워크 환경에서 JPA나 MyBatis 등을 사용할 때 발생하는 DB 에러는 스프링이 내부적으로 `DataAccessException`(RuntimeException의 일종)으로 자동 변환해 주기 때문에 실제로는 정상 롤백됩니다.*

## 3. 실무 솔루션: 일반 예외도 롤백하는 방법

비즈니스 로직을 구현하다 보면 외부 파일 저장(`IOException`)에 실패했을 때, 앞서 수행한 DB 작업도 함께 취소(Rollback)되어야 하는 경우가 매우 많습니다. 

이때는 `@Transactional` 어노테이션의 **`rollbackFor` 옵션**을 사용하여 롤백 대상을 확장할 수 있습니다.

### 💡 권장되는 설정 패턴

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.io.IOException;

@Service
public class OrderService {

    // 모든 예외(Checked Exception 포함) 발생 시 롤백하도록 명시적 설정
    @Transactional(rollbackFor = Exception.class)
    public void processOrder(OrderDto dto) throws IOException {
        
        // 1. DB 작업 (실행 예외 발생 시 자동 롤백됨)
        orderRepository.save(dto.toEntity());
        
        // 2. 외부 파일 생성 (IOException - 일반 예외 발생 가능)
        // rollbackFor 설정 덕분에 여기서 에러가 나도 1번 DB 작업이 안전하게 롤백됩니다.
        fileService.createOrderReceiptFile(dto);
    }
}
