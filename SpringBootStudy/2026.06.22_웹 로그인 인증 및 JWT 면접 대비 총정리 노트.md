# 📚 웹 로그인 인증 및 JWT 면접 대비 총정리 노트

본 문서는 세션과 토큰 기반 인증의 차이점, JWT의 구조, 이중 토큰 전략, 그리고 실무 및 면접 대비 질문 15가지를 초등학생도 이해할 수 있는 쉬운 비유와 함께 정리한 요약본입니다.

---

## 1. 로그인 인증의 두 가지 방법

### ① 세션(Session) 인증: "호텔 장부 방식"
* **개념:** 사용자가 체크인(로그인)을 하면, 서버가 **방명록 장부(서버 메모리/DB)**에 이름과 방 번호를 적어두고 사용자에게는 장부 번호가 적힌 쪽지(**세션 ID**)를 주는 방식입니다.
* **장점:** 주인이 장부를 완벽히 통제하므로 안전합니다. 문제가 생기면 장부에서 이름을 지워버려 즉시 강제 로그아웃 시킬 수 있습니다.
* **단점:** 손님이 수천만 명이 되면 장부 적을 공간(메모리)이 부족해지고, 서버를 여러 대로 늘릴 때 장부를 공유하기가 복잡해집니다.

### ② 토큰(Token/JWT) 인증: "놀이공원 자유이용권 방식"
* **개념:** 입장할 때 돈을 내면 직원이 손목에 **"자유이용권 팔찌"(토큰)**를 채워줍니다. 이후에는 장부를 검사할 필요 없이 팔찌만 보고 통과시켜 주는 방식입니다.
* **장점:** 서버가 손님 이름을 일일이 적어둘 필요가 없어 부담이 없고, 서버를 여러 대로 무한히 늘려도 팔찌 도장만 확인하면 되므로 확장성이 뛰어납니다.
* **단점:** 팔찌를 도둑맞으면(토큰 탈취), 팔찌가 스스로 만료되어 끊어질 때까지 서버가 해커를 강제로 막기가 매우 어렵습니다.

> **💡 보안은 누가 더 나을까?**
> **보안 자체는 서버가 완벽한 제어권을 쥐고 있는 '세션 방식'이 더 유리합니다.** 하지만 대규모 서비스에서는 서버의 부담을 줄이고 쉽게 확장하기 위해 보안을 일부 양보하고 '토큰 방식'을 많이 채택합니다.

## 2. JWT(JSON Web Token)의 구조

JWT 팔찌는 마침표(`.`)를 기준으로 **3가지 구역**으로 나뉩니다.

1. **Header (헤더):** 팔찌의 종류와 어떤 알고리즘으로 묶었는지 적어둔 겉표지입니다.
2. **Payload (페이로드):** "이 사람 아이디는 admin이야" 같은 진짜 정보가 들어있는 구역입니다. 암호화가 아니라 단순히 글자만 바꿔둔 것(Base64 인코딩)이라 누구나 열어볼 수 있으므로, **비밀번호 같은 민감한 정보는 절대 넣으면 안 됩니다.**
3. **Signature (서면/싸인):** 서버만 알고 있는 **비밀키(Secret Key)**로 쾅 찍어놓은 **위조 방지 도장**입니다. 해커가 페이로드의 내용을 바꾸면 도장 마크가 깨져서 서버가 바로 알아챕니다.

### ⚠️ 보안 실무: 환경변수 사용 (하드코딩 금지)
비밀키를 소스코드에 `secret: 나의비밀키1234`처럼 직접 글자로 적어두면 GitHub 등을 통해 전 세계에 유출됩니다. 따라서 코드에는 `${JWT_SECRET_KEY}` 같은 빈칸(플레이스홀더)만 뚫어놓고, 진짜 값은 컴퓨터 환경변수에 숨겨두어 실행할 때 주입받아야 합니다.

## 3. 이중 토큰 전략 (Access vs Refresh)와 자동 재발급 매커니즘

팔찌를 도둑맞는 위험을 방지하기 위해 실무에서는 **2개의 토큰**을 사용합니다.

* **Access Token (입장 티켓):** 15분 정도로 수명이 아주 짧은 진짜 팔찌입니다.
* **Refresh Token (재발급 신분증):** 1~2주 정도로 수명이 길며, 브라우저의 안전한 주머니인 **`httpOnly` 쿠키**에 깊숙이 숨겨둡니다.

### 🔄 3단계 자동 재발급 프로세스 (리액트 ↔ 스프링 협동)
1. **만료:** 사용자가 서비스를 이용하다가 15분이 지나 Access Token 팔찌가 끊어지면, 백엔드(스프링)는 **401 Unauthorized 에러**를 던집니다.
2. **요청:** 프론트엔드(리액트)는 사용자가 모르게 요청을 잠시 대기시키고, 쿠키 주머니에 있던 **Refresh Token을 꺼내어 백엔드에게 재발급 요청**을 보냅니다.
3. **갱신:** 백엔드가 신분증(Refresh Token)을 검증하고 진짜가 맞으면 **새 Access Token을 리액트에게 돌려주고**, 리액트는 새 팔찌를 차고 아까 실패했던 요청을 다시 성공시킵니다.

## 4. 핵심 면접 질문 15선 (토글 답변)

### 1부: 세션 vs 토큰 기초

<details>
<summary><b>Q1. 인증(Authentication)과 인가(Authorization)의 차이는 무엇인가요?</b></summary>

* **인증(Authentication):** "너 누구니?"를 확인하는 과정입니다. 사용자가 아이디와 비밀번호를 입력해 자신이 누구인지 시스템에 증명하는 단계입니다.
* **인가(Authorization):** "너 이거 할 권한 있니?"를 확인하는 과정입니다. 인증된 사용자가 특정 페이지에 접근하거나 기능을 사용할 수 있는지 권한을 체크하는 단계입니다.
</details>

<details>
<summary><b>Q2. 세션 기반 인증 방식의 동작 원리를 설명해 주세요.</b></summary>

1. 사용자가 로그인을 하면 서버는 사용자의 정보를 확인하고, 서버의 메모리(또는 DB)에 세션 정보를 저장한 뒤 고유한 **세션 ID**를 발급합니다.
2. 서버는 이 세션 ID를 HTTP 응답 헤더의 쿠키에 담아서 브라우저로 보냅니다.
3. 브라우저는 이후 모든 요청마다 이 세션 ID 쿠키를 헤더에 실어서 서버에 보냅니다.
4. 서버는 들어온 세션 ID가 자신의 메모리(장부)에 있는지 확인하고 유저를 식별합니다.
</details>

<details>
<summary><b>Q3. 토큰 기반 인증(JWT) 방식의 동작 원리를 설명해 주세요.</b></summary>

1. 사용자가 로그인을 하면 서버는 비밀키(Secret Key)를 사용해 사용자 정보를 담은 암호화된 서명 토큰(JWT)을 생성하여 클라이언트에게 전달합니다.
2. 클라이언트는 이 토큰을 로컬 스토리지나 쿠키 등에 저장해 둡니다.
3. 이후 요청할 때마다 HTTP 헤더(`Authorization: Bearer <토큰>`)에 토큰을 실어서 보냅니다.
4. 서버는 별도의 DB 조회 없이, 자신이 가진 비밀키로 토큰의 **서명(Signature)**만 검증하여 유효한 사용자인지 판단합니다.
</details>

<details>
<summary><b>Q4. 세션 방식과 비교했을 때 토큰(JWT) 방식이 가지는 가장 큰 장점은 무엇인가요?</b></summary>

* **서버의 무상태성(Stateless)과 확장성:** 세션 방식은 서버가 유저의 로그인 상태를 장부(메모리)에 계속 들고 있어야 하므로 서버 부담이 크고, 서버를 여러 대로 늘릴 때 세션 공유 문제가 발생합니다.
* 반면, JWT는 토큰 자체에 유저 정보가 들어있고 서버는 검증만 하면 되므로 상태를 저장할 필요가 없습니다. 따라서 **서버를 무한히 확장(Scale-out)하기에 매우 유리**합니다.
</details>

<details>
<summary><b>Q5. 반대로 토큰(JWT) 방식의 단점이나 한계점은 무엇인가요?</b></summary>

* **강제 로그아웃(제어권)의 어려움:** 토큰은 한번 발급되면 유효기간이 만료될 때까지 서버가 이를 강제로 무효화하기 어렵습니다. 만약 토큰이 탈취당하더라도 서버가 즉시 로그인 세션을 끊어버릴 수 없다는 보안상 취약점이 있습니다.
* **네트워크 데이터 크기:** 토큰 내에 많은 정보를 담을수록 토큰의 길이가 길어지므로, 매 요청마다 발생하는 네트워크 트래픽 데이터가 세션 ID(단순 문자열)에 비해 커집니다.
</details>

### 2부: JWT 심화 및 구조

<details>
<summary><b>Q6. JWT(JSON Web Token)의 구조에 대해 설명해 주세요.</b></summary>

JWT는 마침표(`.`)를 기준으로 세 구역으로 나뉩니다.
1. **Header (헤더):** 토큰의 타입(JWT)과 해싱 알고리즘(예: HS256) 정보가 들어있습니다.
2. **Payload (페이로드):** 토큰에 담을 정보(클레임, Claim)가 들어있습니다. 유저 ID, 권한, 토큰 만료 시간 등이 포함됩니다.
3. **Signature (서명):** 헤더와 페이로드를 서버가 가진 비밀키(Secret Key)로 암호화하여 만든 구역으로, 토큰의 변조 여부를 확인하는 데 사용됩니다.
</details>

<details>
<summary><b>Q7. JWT의 Payload 구역에 사용자의 비밀번호나 주민번호를 넣어도 될까요? 왜 안 되나요?</b></summary>

**절대 안 됩니다.** JWT의 Header와 Payload는 암호화된 것이 아니라 누구나 쉽게 디코딩(Base64)해서 내용을 열어볼 수 있는 문자열입니다. 따라서 누구나 볼 수 있는 Payload에는 비밀번호, 주민등록번호 같은 민감한 개인정보를 절대 포함해서는 안 되며, 유저를 식별할 수 있는 최소한의 정보(예: 유저 DB의 PK, 아이디 등)만 넣어야 합니다.
</details>

<details>
<summary><b>Q8. JWT에서 Signature(서명) 구역은 어떻게 생성되며, 어떤 역할을 하나요?</b></summary>

* **생성 방법:** 인코딩된 헤더와 페이러드의 값을 합친 후, 서버만 알고 있는 **비밀키(Secret Key)**를 이용해 지정된 암호화 알고리즘으로 해싱하여 생성합니다.
* **역할 (무결성 검증):** 클라이언트가 보낸 토큰의 헤더와 페이로드를 서버의 비밀키로 다시 해싱했을 때, 결과가 토큰의 서명 구역과 일치하는지 확인합니다. 만약 해커가 중간에서 페이로드의 유저 권한을 몰래 변경했다면 서명이 일치하지 않으므로, 서버는 **토큰이 위조되었음을 감지**하고 요청을 차단할 수 있습니다.
</details>

<details>
<summary><b>Q9. JWT 도중 만료(Expiration) 시간을 너무 길게 주면 어떤 문제가 생기나요?</b></summary>

보안상 심각한 문제가 발생합니다. 만약 유효기간이 1년인 토큰을 발급했는데 해커가 이 토큰을 탈취한다면, 해커는 1년 동안 아무런 제약 없이 진짜 유저인 척 서버에 접근할 수 있습니다. 서버는 토큰을 강제로 만료시킬 방법이 없기 때문에 큰 피해로 이어집니다. 이를 해결하기 위해 **Access Token과 Refresh Token을 나누어 사용하는 이중 토큰 전략**을 사용합니다.
</details>

<details>
<summary><b>Q10. 스프링 부트 프로젝트에서 JWT 비밀키를 소스코드에 하드코딩하면 안 되는 이유와 해결책은 무엇인가요?</b></summary>

* **이유:** 소스코드를 GitHub 같은 퍼블릭 저장소에 올릴 경우 비밀키가 전 세계에 노출됩니다. 비밀키가 노출되면 해커가 서버인 척 가짜 JWT를 마음대로 생성할 수 있으므로 보안 시스템이 완전히 무너집니다.
* **해결책:** `application.yml` 파일에 비밀키를 직접 적지 않고 `${JWT_SECRET_KEY}` 같은 **환경변수(Environment Variable) 플레이스홀더**를 설정합니다. 그리고 진짜 값은 서버 운영체제 환경변수나 AWS 시스템 매니저 같은 안전한 곳에 저장한 뒤, 애플리케이션 실행 시점에 `@Value` 어노테이션으로 주입받아 사용해야 합니다.
</details>

### 3부: 이중 토큰 및 실무 전략

<details>
<summary><b>Q11. Access Token과 Refresh Token을 나누어 사용하는 '이중 토큰 전략'의 핵심 목적이 무엇인가요?</b></summary>

**보안성과 편의성을 동시에 잡기 위함입니다.** 
* 토큰 탈취 위험을 낮추기 위해 실제로 API 요청에 사용하는 **Access Token의 유효기간은 15~30분 정도로 아주 짧게** 잡습니다. 
* 하지만 기간이 짧으면 유저가 매번 다시 로그인해야 하므로, 유효기간이 긴(예: 1~2주) **Refresh Token을 안전한 곳에 보관**해 두었다가 Access Token이 만료되었을 때 로그인 없이 자동으로 재발급받을 수 있도록 구현합니다.
</details>

<details>
<summary><b>Q12. Access Token이 만료되었을 때, 프론트엔드와 백엔드 간의 재발급 프로세스를 설명해 주세요.</b></summary>

1. 프론트엔드가 만료된 Access Token으로 API 요청을 보내면, 백엔드는 **401 Unauthorized 에러**를 반환합니다.
2. 프론트엔드(리액트 등)는 이 에러를 감지하고, 유저 모르게 저장해 둔 **Refresh Token을 실어서 백엔드의 재발급 API로 요청**을 보냅니다.
3. 백엔드는 Refresh Token의 유효성을 검증하고, 문제가 없다면 **새로운 Access Token을 생성**하여 응답합니다.
4. 프론트엔드는 새로 발급받은 Access Token을 저장하고, 아까 실패했던 API 요청을 다시 시도하여 완료합니다.
</details>

<details>
<summary><b>Q13. Refresh Token은 어디에 보관하는 것이 가장 안전한가요? (보안 취약점 포함)</b></summary>

* **가장 안전한 곳:** 브라우저 쿠키의 **`httpOnly` 및 `secure` 옵션**을 켜고 저장하는 것이 가장 안전합니다. 
* **이유:** `localStorage`에 저장하면 자바스크립트 코드로 접근이 가능하므로 **XSS(크로스 사이트 스크립팅) 공격**에 취약하여 해커에게 토큰을 빼앗길 수 있습니다. 반면 `httpOnly` 쿠키는 자바스크립트 접근이 원천 차단되므로 XSS 공격으로부터 안전합니다. 단, 쿠키는 **CSRF(사이트 간 요청 위조) 공격**에 노출될 수 있으므로 별도의 CSRF 방어 대책(SameSite 옵션 등)을 함께 세워야 합니다.
</details>

<details>
<summary><b>Q14. 만약 해커가 Refresh Token까지 통째로 훔쳐 갔다면, 이를 방어하기 위한 백엔드 실무 전략은 무엇이 있을까요?</b></summary>

두 가지 대표적인 전략이 있습니다.
1. **데이터베이스 저장 및 블랙리스트:** 백엔드 DB(또는 Redis 같은 빠른 메모리 DB)에 발급한 Refresh Token을 저장해 둡니다. 만약 유저가 해킹 신고를 하거나 탈취가 의심되면 DB에서 해당 토큰을 삭제하거나 블랙리스트에 올려 재발급을 막아버립니다. (토큰 방식에 세션의 장점을 일부 결합하는 방식입니다.)
2. **RTR (Refresh Token Rotation) 전략:** Refresh Token을 **단 한 번만 사용할 수 있게** 만듭니다. 프론트엔드가 Refresh Token으로 새 Access Token을 요청할 때, **Refresh Token도 매번 새로 갱신해서 교체**해 버리는 방식입니다. 이렇게 하면 해커가 예전 Refresh Token을 써서 재발급 받으려고 할 때 중복 사용을 감지하여 즉시 차단할 수 있습니다.
</details>

<details>
<summary><b>Q15. 대규모 서비스에서 다수의 서버가 무상태(Stateless)를 유지하면서도, 특정 사용자의 토큰을 강제 만료(로그아웃)시키고 싶다면 아키텍처를 어떻게 설계해야 할까요?</b></summary>

가장 좋은 해결책은 **인메모리 데이터베이스인 Redis(레디스)를 활용**하는 것입니다. 
* JWT 자체는 무상태라 서버가 스스로 멈출 수 없기 때문에, 사용자가 '로그아웃'을 하거나 강제 종료가 필요할 때 해당 사용자의 Access Token을 **Redis에 '블랙리스트'로 등록**하고 토큰의 남은 시간만큼 만료(TTL) 시간을 설정해 둡니다.
* 백엔드 서버들은 모든 요청을 처리하기 전, 아주 빠르게 조회 가능한 Redis를 먼저 체크하여 "이 토큰이 블랙리스트에 있는가?"를 검사합니다. 블랙리스트에 있다면 유효한 토큰이더라도 차단 처리를 합니다. 이 방식을 쓰면 데이터베이스 부하를 최소화하면서도 실시간 제어권을 쥘 수 있습니다.
</details>
